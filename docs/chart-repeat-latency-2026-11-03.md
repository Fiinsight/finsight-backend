# 차트 반복 조회 지연: 원인과 수정

운영 `ec14cfda`의 삼성전자 일봉 요청을 같은 종목·기간·수준·간격으로 연속 측정했다. 이 문서의 수정은 아직 운영에 배포하지 않았다.

## 운영에서 확인한 값

| 요청 | 전체 | 첫 바이트 | 연결+TLS | 압축 전송량 | fallback |
|---|---:|---:|---:|---:|---|
| 첫 요청 | 12.003초 | 12.002초 | 55ms | 6,864B | false |
| 두 번째 | 5.176초 | 5.114초 | 26ms | 6,864B | false |
| 세 번째 | 4.998초 | 4.998초 | 62ms | 6,880B | false |

직전 liveness는 0.299초, 직후는 0.181초였다. 이번 첫 요청은 서버가 이미 깨어 있는 상태다. Render 프록시·서버 대기와 애플리케이션 실행 시간을 현재 운영 응답만으로 완전히 분리할 수는 없다. 예전 24.155초 요청에는 별도 단계 계측이 없어 기상/KIS/DB/AI를 정확한 초 단위로 소급 분해하지 않는다. 이번 첫 요청과 두 번째 요청의 차이 약 6.8초도 KIS 시간만을 뜻하지 않는다.

`/actuator/metrics/cache.gets`는 404로, 운영 캐시 통계는 노출되지 않는다. 운영 캐시 적중률을 직접 읽었다고 주장하지 않는다.

## 캐시와 실행 경로

- `chartResponses`: Caffeine 로컬 캐시, TTL 60초. Redis를 사용하지 않는다. `005930 : D : 0`이며 일봉의 interval은 키에 영향을 주지 않는다. 운영 응답의 fallback은 false이고 연속 요청이므로 fallback 제외나 TTL 만료가 반복 지연의 주원인이라는 근거는 없다.
- `cachedQuote`: 이미 존재하는 `popularStockQuotes`/`kisStockQuotes`를 메모리에서 조회한다. 여기서 KIS 네트워크 호출을 하지 않는다.
- `withDocents`: 캔들 캐시 바깥에서 매번 뉴스 범위 조회, 원인 재매칭, 수집 시작일 조회, 후보 기사의 개별 조회를 수행한다. 개별 도슨트 캐시가 적중해도 이 작업은 남는다.
- 응답은 압축 후 약 6.9KB다. 두 번째 응답의 첫 바이트 이후 시간은 약 62ms이며, 약 5초의 대부분은 첫 바이트를 기다리는 구간이다.

## 통제된 로컬 구간 측정

운영 DB는 `transaction_read_only=on`인 연결로 SELECT만 수행했다. 실제 저장된 기사와 이미 받은 실제 캔들 30개를 사용했다. KIS 가격 요청은 기록된 캔들로 대체했고 AI 네트워크는 사용하지 않았다. JVM은 운영과 같은 단일 CPU 설정·TieredStopAtLevel=1·192MB 힙을 사용했지만 Mac 하드웨어/DB 네트워크는 Render와 다르다. 캔들 캐시 TTL 만료를 배제하기 위해 각 표본 직전에 동일 기록을 base 캐시에 넣었다. 이 표는 Render 종단 응답 시간이 아니다.

| 구간 | 기존 반복 경로 | 수정 후 캐시 적중 1 | 수정 후 캐시 적중 2 |
|---|---:|---:|---:|
| 캔들 캐시 조회 | 0.548ms | 0.102ms | 0.087ms |
| 뉴스·도슨트 전체 | 13,794.804ms | 0.113ms | 0.089ms |
| 위 구간 중 DB | 13,568.781ms / 11조회 | 0ms / 0조회 | 0ms / 0조회 |
| 위 구간 중 매칭·규칙 등 | 226.023ms | 0.113ms | 0.089ms |
| 현재가 캐시 조회 | 0.099ms | 0.006ms | 0.006ms |
| 메서드 전체 | 13,795.451ms | 0.222ms | 0.182ms |

수정 후 첫 읽기 캐시 생성에는 여전히 DB 11조회가 필요했다. 즉 이번 수정은 반복 요청을 개선하며 콜드 요청의 KIS/DB 비용을 없애지 않는다.

## 수정 범위와 검증

1. 뉴스·도슨트가 조합된 결과에 최대 500항목/60초의 `chartReadings` 캐시를 추가했다. 키는 입력 ChartResponse와 읽기 수준이다. 새 캔들·다른 수준을 섞지 않으며 fallback 결과는 저장하지 않는다.
2. 현재가는 읽기 캐시 처리 후 최신 가격 캐시에서 덮어쓴다. 읽기 캐시 때문에 현재가 갱신을 막지 않는다.
3. `Server-Timing`에 `chart`, `news_docent`, `cached_quote` 시간을 넣었다. 배포 후 curl/브라우저 Network에서 실제 구간별 시간을 확인할 수 있다. 인증 필터, 수준 조회, 직렬화, 프록시 시간은 이 세 구간에 포함되지 않는다.
4. 반복 요청의 DB·도슨트 실행 생략, 현재가 갱신, 읽기 수준/캔들 분리, 60초 TTL, 만료 후 재조회, fallback 비저장을 테스트한다.

새 뉴스 재매칭은 최대 60초 지연될 수 있다. 캐시는 프로세스 메모리이므로 재시작 후에는 비어 있다. DB 마이그레이션·AI 핀·LLM 설정은 변경하지 않는다.

배포 승인 후 목표 검증: liveness가 UP인 상태에서 같은 D/W/MINUTE 요청을 60초 내 반복하고, `Server-Timing`과 curl TTFB/전체 시간을 기록한다. 반복 1초 이내 달성 여부는 이 운영 검증 전까지 미확정이다.
