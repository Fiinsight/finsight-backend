# 관심종목 기반 맞춤 학습 1단계 — 2026-10-15

차트에서 저장한 관심종목을 홈 뉴스와 학습 추천에 연결합니다. 새 의존성이나 별도 관리 화면은 추가하지 않습니다.

## 동작

- V16으로 사용자별 관심종목 테이블을 추가합니다. 등록 가능한 종목은 StockCatalog의 6자리 코드이며 지수는 제외합니다.
- 계정당 20개 상한, 추가·삭제 멱등성, 사용자 행 잠금으로 동시 추가 상한을 지킵니다.
- 관심종목 최근 48시간 뉴스를 홈에 먼저 보여주고 전체 피드의 중복을 제외합니다.
- 기존 읽기·판단·퀴즈 제외와 개인화 순서를 유지하며 관심종목 뉴스를 우선합니다. 해당 후보가 없으면 이전 응답을 그대로 반환합니다.
- 차트 첫 종목은 route 지정 → 사용자별 마지막 관심종목 → 첫 관심종목 → 삼성전자 순서입니다. 목록과 저장값을 기다린 후 차트를 로드합니다.
- 새 기사 매칭은 catalog 이름·별칭, 제목 우선, 본문 언급 수를 사용합니다. 짧은 별칭 경계와 일반 명사·자회사 보호를 적용합니다.
- 기존 뉴스 재처리는 저장 종목을 보존합니다. 기존 기사 재매핑은 검토한 preview를 명시적으로 적용할 때만 가능합니다.

## API


모든 API는 Bearer 로그인 세션을 요구하고 `@AuthenticationPrincipal Long userId`만 사용합니다. query/body의 userId로 다른 계정을 지정할 수 없습니다.

| 메서드 / 경로 | 성공 | 검증·동작 |
|---|---|---|
| GET /api/watchlist |200, `[{symbol,name,addedAt}]` | created_at 오름차순, 같은 시각이면 id 오름차순 |
| PUT /api/watchlist/005930 |200, `{symbol:"005930",name:"삼성전자",addedAt:"..."}` | 이미 있으면 기존 시각 그대로.20개일 때 기존 종목 PUT도200 |
| DELETE /api/watchlist/005930 |204, 본문 없음 | 없는 종목도204 |
| GET /api/news/watchlist?limit=5 |200, 기존 NewsBrief 목록 | 본인 관심종목 related_symbol, 현재~48시간 전, 최신순·id 역순, 최대5. limit 1~5, 범위 밖400 |

StockCatalog에 없는 코드,6자리가 아닌 코드, KOSPI/KOSDAQ는 PUT/DELETE에서400입니다. 새 종목을21번째 추가하면409과 `{"message":"관심종목은 20개까지 추가할 수 있어요"}`를 반환합니다. 같은 사용자 행 잠금으로 동시 요청도 상한을 지킵니다.

`GET /api/learning/recommendations`의 기존 readNewsIds·학습 행동 규칙은 유지합니다. 관심 기사 후보가 없으면 이전 Response를 그대로 반환합니다. 관심 기사 자체로 추가하는 추천은 item.basis=WATCHLIST, reason은 관심종목 이름을 사용하고 reasonNewsId는 null입니다. 기존 활동 기반 추천의 이유·순위는 각 그룹 안에서 유지합니다.

프론트 캐시 키는 `['watchlist']`이고 변경 후 watchlist/watchlist-news/learning-recommendations를 invalidate합니다. 로그인 종료 시 기존 App의 queryClient.clear로 타 계정 캐시를 비웁니다. 마지막 종목은 기존 storage 함수를 통해 `finsight:lastWatchlistSymbol:{userId}`에 저장하고, 아직 관심종목인지 검사한 다음 사용합니다.

## 스키마와 기동

`V16__create_user_watchlist.sql`로만 테이블을 생성하고 Hibernate는 `validate`합니다. Flyway 이력이 있는 환경은 정상 기동 시 V16을 적용합니다. 기존 로컬 DB에 Flyway 이력이 없다면 V15와 동일한 스키마인지 확인한 후 README의 명시적 baseline 방법을 사용해야 합니다. 기본 로컬 설정은 Flyway 비활성이므로 V16 적용 없이 기동하면 검증 오류가 납니다.

이번 작업에서 실행 중 서비스 재시작, 기존 DB 마이그레이션·재매핑 적용, 환경 설정 변경, 유료 LLM 호출은 하지 않았습니다. AI 코드는 변경하지 않았습니다.

## 검증 범위

분리된 feature 브랜치에서 backend `./gradlew clean test`가 통과했습니다(Java 218건 중 migration 전용 7건은 기본 실행에서 제외, Python 보조 도구 19건 통과). 제외된 7건은 임시 PostgreSQL에서 별도 실행하여 V1~V16 migration/validate, 실제 API 소유자 격리·동시 20개 제한을 모두 확인했습니다. frontend 100개 테스트·타입 검사·web export도 통과했습니다.
